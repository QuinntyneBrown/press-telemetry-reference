# L2 - Detailed Requirements

Telemetry point shape used throughout this document:

```json
{ "deviceId": "press-01", "metric": "temperature", "value": 87.4, "timestamp": "2026-08-15T12:00:00Z" }
```

`deviceId` and `metric` are strings of 1-64 characters matching `[A-Za-z0-9_-]+`; `value` is a
finite number; `timestamp` is ISO-8601 UTC.

Retry backoff policy referenced below: exponential backoff starting at 1 second, doubling to a
30-second cap.

---

## L2-001: MQTT subscription and reconnection
**Traces to:** L1-001

The ingestion worker shall connect to the configured MQTT broker on startup and subscribe at
QoS 0 to a configurable topic filter (default `telemetry/#`). At-most-once delivery is an
accepted trade-off for this reference (a missed dashboard sample is tolerable, and QoS 0
removes any need for duplicate-delivery handling); the README must state this. The connection
shall recover automatically using the standard backoff policy; broker unavailability must
never terminate the worker process.

**Acceptance Criteria:**
1. Given the broker is reachable and the worker starts, when startup completes, then the worker is subscribed to the configured topic filter at QoS 0 and logs the broker address and topic filter.
2. Given the worker is running, when the broker connection drops, then the worker retries per the backoff policy (1s doubling to a 30s cap), logs each state change, and stays alive.
3. Given the connection was lost, when the broker becomes reachable again, then the worker re-subscribes and messages published after re-subscription are ingested without a restart.
4. Given the broker is unreachable at startup, when the worker starts, then it keeps retrying per the backoff policy instead of exiting.

---

## L2-002: Telemetry message validation
**Traces to:** L1-001

The worker shall parse each MQTT message body as a JSON telemetry point and validate it against
the shape above. Invalid messages are dropped with a warning log; they never crash the worker
and are never written to storage.

**Acceptance Criteria:**
1. Given a message whose body is a valid telemetry point, when it arrives, then it is accepted for persistence and live fan-out.
2. Given a message with malformed JSON, a missing required field, a non-finite `value`, an unparseable `timestamp`, or a `deviceId`/`metric` violating the 1-64 character `[A-Za-z0-9_-]+` rule, when it arrives, then it is dropped, a warning is logged with the failure reason, and nothing is written to Couchbase or pushed to clients.
3. Given a burst of invalid messages, when they arrive, then the worker continues processing subsequent valid messages normally.

---

## L2-003: Couchbase time series writes
**Traces to:** L1-002

The worker shall append each valid telemetry point to Couchbase time series documents keyed by
`deviceId`, `metric`, and an hourly time bucket, following Couchbase's time series document
format (`ts_start`, `ts_end`, `ts_data`) so points are retrievable with the `_timeseries()`
SQL++ function. Couchbase provides the document format convention and the query function but
no dedicated time series write API: the worker itself creates and appends the bucketed
documents via key-value sub-document operations. The worker is the sole telemetry writer in
the solution.

**Acceptance Criteria:**
1. Given a valid telemetry point is ingested, when the write completes, then a `_timeseries()` query ordered by timestamp for that `deviceId`/`metric` and a range covering its timestamp returns the point with its original value and timestamp.
2. Given 1,000 valid points for one `deviceId`/`metric` are ingested, when writes complete, then a `_timeseries()` range query ordered by timestamp returns all 1,000 points exactly once, in ascending order.
3. Given points whose timestamps span two hourly buckets, when a range covering both is queried, then points from both time series documents are returned.
4. Given the full solution source code, when it is searched for telemetry write operations against Couchbase, then such operations exist only in the ingestion worker project.

---

## L2-004: Persistence failure handling
**Traces to:** L1-002

When a Couchbase write fails, the worker shall retry up to 3 attempts per the standard backoff
policy and then drop the point with an error log. Persistence failures must not stop ingestion
or live fan-out of subsequent points.

**Acceptance Criteria:**
1. Given Couchbase is temporarily unavailable, when a write fails, then the worker retries up to 3 attempts with backoff before dropping the point and logging an error that includes `deviceId`, `metric`, and `timestamp`.
2. Given Couchbase is down for an extended period, when messages keep arriving, then the worker remains running and resumes successful writes once Couchbase recovers.
3. Given a write ultimately fails after retries, when subsequent valid points arrive, then they are processed normally (no stalled pipeline).

---

## L2-005: Historical range query endpoint
**Traces to:** L1-003

The API shall expose `GET /api/telemetry/{deviceId}/{metric}?from={iso}&to={iso}` returning the
stored points for that series within `[from, to)` as a JSON array of `{ "timestamp", "value" }`
ordered by ascending timestamp, reading via Couchbase's `_timeseries()` function. Ranges wider
than 24 hours are rejected.

**Acceptance Criteria:**
1. Given stored points for a series, when a request specifies a range covering some of them, then the response is `200` with exactly the points in `[from, to)`, ascending by timestamp.
2. Given a series or range with no data, when the request is made, then the response is `200` with an empty JSON array.
3. Given `from` or `to` is missing or not valid ISO-8601, when the request is made, then the response is `400` with a ProblemDetails body naming the invalid parameter.
4. Given `from >= to`, when the request is made, then the response is `400` with a ProblemDetails body stating the range is invalid, naming both parameters.
5. Given a requested range wider than 24 hours, when the request is made, then the response is `400` with a ProblemDetails body stating the 24-hour maximum window.

## L2-006: Dashboard snapshot endpoint
**Traces to:** L1-003

The API shall expose `GET /api/telemetry/latest` returning the most recent point for every
known `deviceId`/`metric` series, giving the dashboard everything it needs for first render in
a single request. Known series and their latest points must be derived by querying the time
series data itself (an aggregate query over the `_timeseries()` documents) — never by
maintaining a separate latest-value record, which would be a second write path forbidden by
L1-002. Query cost at reference scale is acceptable.

**Acceptance Criteria:**
1. Given points exist for three series, when `GET /api/telemetry/latest` is called, then the response is `200` with exactly three entries, each containing `deviceId`, `metric`, `value`, and `timestamp` of that series' newest point.
2. Given a series receives a newer point, when the endpoint is called again, then that series' entry reflects the newer value and timestamp.
3. Given no telemetry has ever been stored, when the endpoint is called, then the response is `200` with an empty JSON array.
4. Given the full solution source code, when it is searched, then no code maintains a latest-value document or series registry outside the time series documents themselves.

---

## L2-007: SignalR live push hub
**Traces to:** L1-004

The API shall expose a SignalR hub at `/hubs/telemetry` that broadcasts every ingested
telemetry point to all connected clients as a `telemetry` message. Per-device server-side
filtering (subscription groups) is deliberately omitted per L1-008: the dashboard renders all
series, so subscription machinery adds complexity without payoff at reference scale.

**Acceptance Criteria:**
1. Given a connected client, when a valid point for any device is ingested by the worker, then the client receives a `telemetry` message containing that point within 1 second.
2. Given three connected clients, when a point is ingested, then all three receive it.
3. Given a client connects while ingestion is already running, when new points are ingested, then the client receives only points ingested after it connected (history comes from REST, never from the hub).

---

## L2-008: Worker fan-out via Redis backplane
**Traces to:** L1-004

The worker shall publish each valid telemetry point through the Redis backplane so every API
instance delivers it to its own connected clients. The worker hosts no HTTP server and accepts
no client connections, and the API's live push path never reads from Couchbase. Points
ingested during a Redis outage are persisted but not retroactively delivered to already-
connected clients; this gap is an accepted simplicity trade-off that the README must document.

**Acceptance Criteria:**
1. Given two API instances with one connected client each, when the worker ingests a valid point, then both clients receive it.
2. Given Couchbase is stopped and Redis is up, when the worker ingests a valid point, then a connected client still receives it within 1 second (live delivery does not depend on Couchbase).
3. Given the worker process is running, when its listening sockets are enumerated, then it exposes no HTTP or SignalR listener.
4. Given Redis is temporarily unavailable, when points are ingested, then the worker continues persisting to Couchbase and logs the fan-out failure; live delivery resumes for newly ingested points when Redis recovers.

---

## L2-009: First render hydrated from REST
**Traces to:** L1-005

The dashboard shall load its initial data by calling the snapshot endpoint (and the range
endpoint for any visible chart) through TanStack Query, and shall render from that cache
without waiting for any SignalR traffic.

**Acceptance Criteria:**
1. Given the API is reachable, when the dashboard loads, then current values render from REST responses even if no SignalR message ever arrives.
2. Given the dashboard is loading, when queries are in flight, then a loading state is shown, and when a query fails, then an error state with a retry action is shown instead of a blank or broken layout.
3. Given a hydrated dashboard with a stable hub connection and a focused tab, when network traffic is observed for 60 seconds of live updates, then no telemetry REST requests occur (reconnect-triggered refetches per L2-012 excluded).

---

## L2-010: Live updates patch the query cache
**Traces to:** L1-005

Incoming SignalR telemetry messages shall update the existing TanStack Query cache in place —
patching the snapshot entry and appending to any cached range data — rather than triggering
refetches.

**Acceptance Criteria:**
1. Given a hydrated dashboard, when a `telemetry` message arrives, then the corresponding tile and chart reflect the new point without any new REST request.
2. Given a message arrives for a series with cached range data and its timestamp is newer than the newest cached range point, when the cache is patched, then the point is appended in timestamp order with no duplicates.
3. Given a message arrives carrying a timestamp older than the newest cached range point for its series, when the cache is patched, then the point is discarded from range data (the reconnect refetch of L2-012 heals any resulting gap).
4. Given a message arrives carrying a timestamp older than the newest cached snapshot value for its series, when the cache is patched, then the snapshot's latest value is not regressed to the older point.

---

## L2-011: ~1 Hz UI update throttle
**Traces to:** L1-005

The frontend shall buffer incoming SignalR messages and commit them to the query cache in
batches at approximately 1 Hz, regardless of inbound message rate. Within each flush, the
latest value per series wins for the snapshot entry, while all buffered points are appended to
cached range data (subject to the ordering rules of L2-010).

**Acceptance Criteria:**
1. Given messages arrive at 50 per second for one series, when 10 seconds elapse, then the cache is committed no more than ~10 times (at most 15) and the tile shows the most recent value after the final flush.
2. Given a single message arrives on an otherwise idle stream, when the next flush occurs, then it is visible within 1 second of arrival (no indefinite buffering).
3. Given messages for multiple series arrive within one flush interval, when the flush runs, then each series shows its own most recent value.
4. Given N in-order messages for one series with cached range data arrive within one flush interval, when the flush commits, then all N points are appended to the range cache in timestamp order — latest-wins applies only to the snapshot entry.

---

## L2-012: SignalR connection lifecycle
**Traces to:** L1-005

The frontend shall connect with `@microsoft/signalr` using a reconnect policy that retries
indefinitely — custom retry delays passed to `withAutomaticReconnect`, or an `onclose` handler
that restarts the connection — because the library's default policy stops after four attempts.
On reconnection the client shall invalidate telemetry queries so missed points are backfilled
from REST, and connection state shall be visible in the UI.

**Acceptance Criteria:**
1. Given the hub connection drops and is later restored, when the client reconnects, then it invalidates telemetry queries and values missed during the outage appear after refetch.
2. Given the hub is unreachable for longer than 60 seconds, when it becomes reachable again, then the client still reconnects without a page reload (retries never stop).
3. Given the connection is lost, when the dashboard is viewed, then a visible indicator shows the disconnected/reconnecting state, and returns to a connected state after recovery.
4. Given the dashboard tab is closed or the component owning the connection unmounts, when teardown runs, then the hub connection is stopped and no reconnect loop persists.

---

## L2-013: Dashboard core library
**Traces to:** L1-006

The workspace shall contain a `dashboard-core` library of reusable, presentation-focused
components — at minimum a time series chart, a latest-value tile, a connection status
indicator, and a dashboard grid layout — plus the theme. Components receive data via props and
perform no data fetching themselves. One consuming application satisfies L1-006.

**Acceptance Criteria:**
1. Given the workspace, when it is inspected, then `dashboard-core` exists as a library separate from any application and exports the chart, tile, status indicator, grid, and theme.
2. Given the `dashboard-core` source, when it is searched, then it contains no REST, SignalR, or TanStack Query usage — components are driven entirely by props.
3. Given a dashboard application, when it renders telemetry, then it does so through `dashboard-core` components rather than app-local duplicates.

---

## L2-014: Dynamic public libraries
**Traces to:** L1-006

Each workspace library shall expose a single public entry point (its package export); deep
imports into library internals are disallowed. Dashboard views live in publishable view
libraries, and the application loads each view library dynamically — a dynamic `import()` of
the library's public entry point — so the libraries themselves are both public (publishable,
explicit API) and dynamic (code-split, loaded on demand).

**Acceptance Criteria:**
1. Given application code imports from a library, when lint/build runs, then imports from the library's public entry point succeed and deep imports into internal modules fail the check.
2. Given a production build, when its output is inspected, then each view library's entry point lands in its own chunk and the initial bundle contains no view library code.
3. Given a user navigates to a view for the first time, when navigation occurs, then that view library's chunk is fetched on demand and the view renders.

---

## L2-015: Dark-mode theme
**Traces to:** L1-007

The UI shall ship a single dark theme in the spirit of Open MCT: dark neutral surfaces,
high-contrast text and data, restrained accent colors for live/status emphasis. All colors are
defined as design tokens (CSS custom properties) in `dashboard-core`; components never
hard-code colors.

**Acceptance Criteria:**
1. Given the theme's surface background tokens, when their computed values are inspected, then each resolves to a color with relative luminance <= 0.1 and HSL saturation <= 10%, and body text against its background meets WCAG AA contrast (>= 4.5:1).
2. Given the frontend source outside the theme definition, when it is searched for color literals, then component styles reference tokens instead of hard-coded color values.
3. Given the status indicator and live-updating values, when they render, then they use accent tokens distinct from static text.

---

## L2-016: Responsive dashboard layout
**Traces to:** L1-007

The dashboard shall adapt fluidly across extra-small (<576px), small (>=576px), medium
(>=768px), large (>=992px), and extra-large (>=1200px) viewports: a single column below 576px,
at least two columns at >=768px, and at least three at >=1200px, with charts resizing to their
containers. A fluid auto-fit CSS grid meeting these outcomes is an acceptable implementation;
no named breakpoint system is required.

**Acceptance Criteria:**
1. Given a 320px-wide viewport, when the dashboard renders, then tiles and charts stack in a single column with no horizontal page scrolling.
2. Given a 768px-wide viewport, when the dashboard renders, then the grid shows at least two columns; given a 1200px-wide viewport, then at least three.
3. Given the viewport is resized continuously from 320px to 1920px, when the dashboard reflows, then no content is clipped or overlapped at any width.
4. Given a chart is visible, when its container is resized, then the chart redraws to fit the container.

## L2-017: Simplicity constraints
**Traces to:** L1-008

The solution shall consist of exactly two backend deployables (ingestion worker, API), one
frontend workspace, and exactly three external infrastructure services (MQTT broker, Couchbase,
Redis). Telemetry has one write path and one live path; no component beyond those named here
may be introduced.

**Acceptance Criteria:**
1. Given the repository, when its projects are enumerated, then the backend contains exactly one worker deployable and one API deployable (test projects excluded).
2. Given the deployment configuration, when its services are enumerated, then external infrastructure is exactly: one MQTT broker, Couchbase, and Redis.
3. Given the source code, when it is reviewed, then telemetry is written to storage by exactly one code path in the worker and pushed live by exactly one code path through the Redis backplane — no secondary stores, exports, or mirrors.

---

## L2-018: Secrets and configuration hygiene
**Traces to:** L1-009

All connection strings and credentials shall come from configuration (environment variables or
local override files excluded from source control). The repository must contain no real
secrets; committed defaults must reference only local development infrastructure.

**Acceptance Criteria:**
1. Given the repository, when a secret scanner (gitleaks with default rules) runs over the full git history, then it reports no findings, and committed defaults reference only localhost/container hostnames with well-known development credentials documented in the README.
2. Given the worker and API start, when configuration is read, then Couchbase, Redis, and MQTT settings are supplied via configuration and an environment variable override takes precedence over committed defaults.
3. Given a required setting is absent, when a backend process starts, then it fails fast with a log message naming the missing setting rather than starting in a broken state.

---

## L2-019: API hardening baseline
**Traces to:** L1-009

The API shall validate all route and query parameters (per the telemetry point shape rules),
return RFC 7807 ProblemDetails for client errors, and enforce a CORS allowlist of configured
origins. The README shall state that end-user authentication is out of scope for this
reference.

**Acceptance Criteria:**
1. Given any REST endpoint, when called with a `deviceId` or `metric` violating the 1-64 character `[A-Za-z0-9_-]+` rule, then the response is `400` ProblemDetails and no query reaches Couchbase.
2. Given a browser origin not in the configured allowlist, when it makes a cross-origin request, then CORS headers do not permit it; a configured origin is permitted.
3. Given the README, when it is read, then it explicitly documents that authentication/authorization are out of scope and what a consumer must add for production use.

---

## L2-020: Docker Compose development environment
**Traces to:** L1-010

The repository shall include a Docker Compose file provisioning the MQTT broker, Couchbase
Server (pinned to a version with time series support, 7.6 or later), and Redis for local
development, plus README instructions from clean clone to running dashboard. The external
telemetry publisher remains out of scope; the README shall show how to publish a sample
message manually to verify the pipeline.

**Acceptance Criteria:**
1. Given a clean clone with Docker available, when the documented setup commands are run, then the broker, Couchbase 7.6+ (with required bucket/scope/collection initialized), and Redis are running and healthy.
2. Given the infrastructure is up, when the documented run commands for worker, API, and frontend are executed, then the dashboard loads in a browser using only committed default configuration.
3. Given the running system, when the README's sample MQTT publish command is executed, then the published value appears on the dashboard within 3 seconds.

---

## L2-021: Health and structured logging
**Traces to:** L1-010

The API shall expose `GET /health` reporting readiness of its Couchbase and Redis dependencies.
Both backend processes shall emit structured logs, including connection state changes for MQTT,
Couchbase, and Redis, with level configurable via configuration.

**Acceptance Criteria:**
1. Given Couchbase and Redis are reachable, when `GET /health` is called, then the response is `200` with per-dependency status; given either is down, then the response is `503` naming the unhealthy dependency.
2. Given the worker runs through a broker outage and recovery, when logs are inspected, then structured entries record each connect, disconnect, and retry with timestamps.
3. Given the log level is set to `Warning` via configuration, when the system runs normally, then per-message ingestion logs are suppressed while warnings and errors still appear.
