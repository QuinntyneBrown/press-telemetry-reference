# L1 - High-Level Requirements

Reference solution: a radically simple telemetry dashboard. An external service (out of scope)
publishes telemetry over MQTT. A .NET backend ingests it into Couchbase time series storage and
fans it out live; a React frontend renders historical and live telemetry in a responsive,
dark-mode dashboard. The guiding constraint is low complexity: one write path, two backend
deployables, no gold plating.

## L1-001: Telemetry ingestion from MQTT
The system must subscribe to telemetry published by an external service over MQTT and convert
each message into a validated telemetry point. The external publisher and the MQTT broker are
not part of this solution; the ingestion worker is a consumer only.

## L1-002: Time series persistence in Couchbase
The system must persist telemetry points to Couchbase using its native time series
functionality. There is exactly one write path: the ingestion worker is the only component
that writes telemetry, and each point is written once (no dual-writing to secondary stores
or parallel formats).

## L1-003: Historical telemetry REST API
An ASP.NET Core API must expose REST endpoints for historical time-range queries and for the
snapshot data the dashboard needs on first render.

## L1-004: Live telemetry distribution via SignalR
The API must expose a SignalR hub that pushes telemetry to connected dashboard clients as it
is ingested. The ingestion worker fans out through a Redis backplane so that ingestion and
web tiers scale independently: any number of API instances deliver the same live stream, and
the worker never handles client connections.

## L1-005: Frontend live data layer
The React frontend must hydrate its first render from the REST API using TanStack Query, then
keep the same query cache current by patching it from SignalR messages — no polling and no
refetch-per-message. UI updates are throttled to approximately 1 Hz regardless of inbound
message rate.

## L1-006: Modular frontend architecture
The frontend must be organized as a workspace containing a reusable dashboard core library,
a dashboard application that consumes it, and publishable ("public") libraries with explicit
public entry points that the application loads dynamically — each view library is code-split
and imported on demand. One application and the libraries these requirements name satisfy
this requirement; additional applications or libraries are permitted only when they serve a
requirement, never to demonstrate workspace shape.

## L1-007: Responsive dark-mode dashboard UI
The dashboard must present telemetry in a dark-mode visual style in the spirit of Open MCT
(dark surfaces, high-contrast data, restrained accent colors) and must remain usable across
all viewport sizes from extra-small (<576px) through extra-large (>=1200px).

## L1-008: Radical simplicity
As a cross-cutting constraint, the solution must stay minimal: exactly two backend
deployables (ingestion worker and API), one frontend workspace, and exactly three external
infrastructure dependencies (MQTT broker, Couchbase, Redis). No speculative abstractions,
no additional queues, brokers, caches, or databases, and no features beyond these
requirements.

## L1-009: Security essentials
The system must apply baseline security appropriate to a reference solution: all external
input (MQTT payloads and HTTP parameters) is validated, secrets never live in source
control, and the API restricts cross-origin access to configured origins. End-user
authentication and authorization are explicitly out of scope for this reference and must be
documented as such.

## L1-010: Runnable reference environment
A developer must be able to clone the repository and reach a running dashboard using only
documented commands, with local infrastructure provisioned by Docker Compose, and must be
able to observe system health through a health endpoint and structured logs.
